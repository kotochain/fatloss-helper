# 减脂小助手

[![测试](https://github.com/kotochain/fatloss-helper/actions/workflows/ci.yml/badge.svg)](https://github.com/kotochain/fatloss-helper/actions/workflows/ci.yml)

**线上地址（手机上用这个）**：https://kotochain.github.io/fatloss-helper/

---

一个只给一个人用的减脂助手：说一句话就能记饮食，自动算热量和碳蛋脂，并给出「今天接下来怎么吃」和「今天练什么」。

**它就是一个网页应用**：不需要服务器、不需要注册、不需要电脑常开。
装到手机主屏幕后就是一个 App（有图标、全屏、断网也能用）。

- **记录**：「今天中午在食堂吃了碗牛肉面，加了个蛋」→ 自动拆成条目，改完确认即可。
- **算账**：按你的身高体重活动量算出每天吃多少、蛋白脂肪碳水各多少克（自带安全下限）。
- **推荐**：每餐吃什么、吃多少克（含烹调油额度）；有氧动作按你**当天能用的器械**排，机器被占了能一键换。
- **校准**：「体重」页按实际掉秤速度告诉你该多吃还是少吃 —— 比任何公式都准。
- **正反馈**：小植物随记录生长、16 个行为类徽章、每周小结、解锁时的小庆祝 ——
  减脂的痛苦在于反馈太慢，这些是为了让你愿意记下去。
- **AI**：在手机上填一次密钥就能用（浏览器直连服务商，国内几家都实测过允许直连）。不填也能用，走内置的离线识别。
- **更新提示**：每次更新后第一次打开会弹「更新了什么」；手机上的版本旧了会提醒刷新 —— 记录不会丢，也不会打断正在记的一笔。

**数据全部存在使用者的手机上（浏览器本地存储），不上传。** 换手机或清缓存前记得在「体重」页导出存档。

## 〇、正反馈设计（2026-10-16）

减脂是件反馈很慢的事：努力两周，体重可能一动不动。所以这个工具专门做了一套正反馈，
但**刻意避开了常见的坑**：

| 做法 | 为什么这么做 |
| --- | --- |
| 徽章只和**行为**有关（记录了、吃够蛋白、动起来、敢上秤） | 行为是你能控制的，结果是控制不了的。只奖励结果＝逼你走捷径 |
| **没有**「今天吃得少」「掉秤快」这类徽章 | 那等于鼓励节食，短期有效、长期伤身体 |
| 断记录**没有任何惩罚**：植物不会枯萎、徽章不会收回 | 放弃的代价必须是零。一次中断就清零的游戏，会让人直接退出 |
| 小植物按**累计**天数生长，不看连续 | 断几天回来，它还是原来那么大，不会"白费" |
| 体重上涨也照样给正反馈 | 肯站上秤这个行为本身就值得肯定 |
| 周报把**行为放前面**，体重只作为其中一个数字 | 每天看体重会焦虑，看行为不会 |
| 同一个徽章只庆祝一次，动画可关 | 惊喜重复三次就变成噪音 |

**只有 AI 一种模式（v42 起；v44 起新手引导必须当场配好才能往下走）**：说一句、教练的「说细一点」需要你自己填一次 API 密钥
（AI 设置里有 5 分钟教程，以 DeepSeek 为例）。

- 没配 AI 时**一个请求都不发**：「说一句」会直接说「还没配置 AI」并给「去配 AI」的按钮，不拿本地词表硬猜。
- 不配 AI 也能好好记：搜食物库、只填热量、照包装营养成分表都完整可用；教练会给本地版建议，周洞察照常算。
- 配好密钥后自动生效：记录页右上角显示「AI 已开启」；点它或「我的」页顶部都能进 AI 设置。

> 设计原则：**AI 负责「听懂和估」，本地负责「核对和记录」。**
> 份量、热量、营养素这些数字，AI 可以估（本地库里没有的菜要靠它），但必须过本地校验
> （上下限 + 4/9/4 对账）；本地库和「我的食物」命中时以本地数字为准。
> 所以没配 API 也不会变成「残废版」—— 只是「说一句」要先把 AI 配起来。
>
> 相关待办见 GitHub issue：#1 会员制度、#21 看图模型单独选、#22 备份附上读不出来的存档。

**份量不确定时会反问你**：说「一碗牛肉面」，你会看到
「这个份量我是猜的 —— 你没说这一份多大」+ 三个档位（小碗 420 / 正常 600 / 大碗 840 克），
点一下合计热量实时更新。说清了（「200 克米饭」「两个鸡蛋」「一罐可乐」）就不问，不啰嗦。

**「你的规律」**：从你自己的记录里算出规律（蛋白吃够的日子热量是不是更低、运动日吃了多少、
这十几天的热量大头是哪个食物、周末比工作日多多少、体重趋势）。
**纯本地计算，不联网、不调用 AI**。少于 4 天记录时不给结论 —— 数据不够编出来的「规律」是害人的。
文案只讲事实不评判（「外卖日平均多 320 kcal」而不是「你外卖吃太多了」），有测试扫描把关。

**称呼是可选的**：可以在「你的资料」里填一个称呼，会用在问候和周报里；
留空就不称呼。**代码里没有任何硬编码的人名**（有测试把关），
所以换个人用完全不会有「这不是给我做的」的感觉。

具体有什么：小植物（6 个阶段，🌱→🌳）、16 个徽章（带进度条，差多少一眼看到）、
每周一的小结（含一周格子图）、解锁时的彩条庆祝 + 一句具体的肯定
（是「吃够蛋白是减脂期最值钱的一件事」这种，不是「加油你最棒」）。
记完一笔后还有即时反馈：「第一笔记录，成了。」「今天的蛋白质达标了，这条最值钱。」

## 〇·二、两个新增能力（2026-10-16）

### 1. 「说一句就记上」
不用在列表里翻找。在「记录」页直接写：

> 今天中午在食堂吃了碗牛肉面，加了个蛋

它会拆成「牛肉面 600 克 + 鸡蛋 1 个」，**先把结果给你看**（每条的克数都能直接改），确认后再记上。
份量说不清时会反问你（「大概多大一碗？小碗/普通碗/大碗」）。

**AI 接通前也能用**：内置的离线识别能认 100 多种常见说法（食堂打饭、盖饭、麻辣烫、火锅、饺子、
奶茶、外卖套餐……），认不出来的会明确说「这句我没认出来」，不会瞎猜一个数字。

### 2. 「今天练什么」跟着器械走
推荐页先问你今天有什么器械（跑步机 / 椭圆机 / 单车 / 划船机 / 登山机 / 徒手……），再出方案。

- 计划写的是**爬坡走，但跑步机被占了**——把「跑步机」取消勾选，方案会立刻变成椭圆机匀速，并写清「同样练心肺和腿臀，膝盖零冲击」。
- 想做的机器没空时，点「看替代方案」，会按你**实际能用的器械**给出替代动作，并说明为什么能替代（练到同一件事 + 强度对比）。
- 时间紧（20 分钟）时优先给间歇方案；时间宽裕（40 分钟以上）才推长时间中低强度。
- 勾过的器械、选过的目标和时长都会记住（存在这台手机上），下次打开不用重选。

力量训练按你说的先放着，现在全部是有氧 + 徒手循环。

## 〇·三、AI 教练（2026-10-20，v21）

今天页新增「接下来怎么吃 → 问教练」。点开就能看到**按今天记录算好的建议**：还能吃多少、
蛋白还差多少、具体吃哪两样（克数、热量、蛋白都写清楚）。

两条路，同一份事实：

| | 不配 AI（本地版） | 配了 AI |
| --- | --- | --- |
| 数字 | 本地算 | 本地算（同一份） |
| 措辞 | 模板化但完整 | 模型组织成 3~5 句人话 |
| 花钱 | 0 | 点「让 AI 说细一点」才发一次请求 |

**最重要的一条：AI 不许算数。** 给模型的是一份「事实清单」（今天已吃/还能吃/蛋白缺口/建议搭配/
最近 7 天概况），它只负责措辞。回来的话还要过一道校验：

- 出现清单外的数字（比如模型自己编「999 kcal」）→ 整段作废，退回本地版；
- 出现「练了可以多吃」「奖励自己」这类暗示 → 同样作废；
- AI 没接上（没网/密钥失效/超时）→ 照样显示本地版，只多一行说明，不弹错误页。

这样即使模型抽风，你看到的数字也永远和记录对得上。

## 〇·四、拍照读表用真模型跑过了（2026-10-21，v23）

之前「照包装 → 拍照读表」只用假服务商验过（证明图片塞得进去、表单填得上），
没证明真模型能不能读懂中国包装。这次拿真密钥（DeepSeek，`deepseek-chat`，能看图）跑了一遍。

**结论：三张常见照片全读对，第四张「拍糊了」暴露了一个真问题。**

| 照片 | 结果 |
| --- | --- |
| 每 100 克的表（1078 kJ / 蛋白 9.2 / 脂肪 3.6 / 碳水 46.5） | 7 个字段全对，1.3 秒 |
| 「每份 45 克」的表（190 kcal） | 全对，连 baseGrams=45 都对，1.1 秒 |
| 包装正面（根本没有表） | 正确地回「没有找到营养成分表」，没有硬编数字，0.9 秒 |
| 拍糊了（字很小、失焦） | **第一次把整行读错位**：蛋白质读成能量那行的 NRV%（13）、脂肪读成 9.2 |

那一行错位很危险：数字全是非空的、看着挺像，只有按 4/9/4 折一遍才发现对不上（323 vs 258 kcal）。
修了两层：

1. **提示词**：明确要求「数字必须和项目名同一行」，并且输出前按 4/9/4 自查一遍，差得远就重看或留空。
   改完同一张糊照片读对了。
2. **界面兜底**（不靠模型自觉）：照片读出来的数字如果自己对不上（>20%），预览里直接说
   「这张照片可能没读准，重拍一张会更快：拍满画面、正对着、别反光 —— 先别直接保存」。
   你自己动手改过任何一个数，这句话就不再出现（那时该劝的是「核对你改的」，不是「重拍」）。

顺手还修了一个坑：把模型名写成 `deepseek-flash` 时，它会先把答案写进思考过程，
额度不够时正文是空的 —— 界面上原来显示「没读出来：服务商没有返回内容」，看着像断网。
现在会明确说「模型把额度花在思考上了」，并告诉你用 `deepseek-chat`。

**可复现**：`DEEPSEEK_API_KEY=sk-xxx npm run check:label-live`
（会渲染四张「照片」到 `.selfcheck/label-live-*.jpg`，可以自己看长什么样；没有密钥时直接跳过。）

## 〇·五、界面图标：内联 SVG（2026-10-21，v26 → v27，issue #9）

以前整界面靠 emoji 当图标：**123 处、约 50 种**（徽章 55、器械 24、界面 29、洞察 14）。
问题不是「不好看」这么简单：

- 同一颗 emoji 在 iPhone / 安卓 / Windows 上是三套完全不同的画 —— 产品在别人手机上长什么样，我们控制不了；
- 风格不统一：有的带底色块、有的纯线、有的立体渐变；
- 读屏软件会念「米饭 emoji」这种噪音；
- 换字号时 emoji 的宽窄会变，CI 上真出现过单个 emoji 撑到 37px 挤到旁边文字。

现在全部换成 **内联 SVG**（`js/icons.js`），不引外部字体、不引 CDN、不加位图，断网照样显示：

| 用途 | 形式 |
| --- | --- |
| 按钮 / 分段 / 洞察 / 器械 | 单色线框，24 网格、1.6 描边、跟着 `currentColor` 变 |
| 设置页每一行（v27） | **38px 彩色圆角图标块 + 23px 线框**，一行一色（资料=玫红、AI=金、成长=绿、备份=蓝灰、清空=砖红、引导=藕紫、关于=灰） |
| 徽章（22 种字形，含里程碑/周报）（v27） | **12 道花边的勋章底 + 内圈渐变圆盘 + 白色实心字形**，48~58px；没解锁的显示灰版 + 右下角小锁 |
| 植物（6 个阶段） | 2~3 色插画（发芽 → 叶子 → 盆栽 → 开花 → 向日葵 → 树） |

**为什么不用 AI 生成图片**：位图在断网时没法缓存成矢量、不同手机分辨率下会糊、颜色也没法跟着界面主题走。
这个 App 的核心约束是「装到桌面、断网能用、每台手机长得一样」，所以素材必须是矢量的。
徽章里 22 个实心字形用了 **Phosphor Icons（MIT 许可）** 的路径数据，内联进 `js/icons.js`，
运行时不加载任何外部资源；许可全文在 [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md)。

**护栏**（防止过两周又混进 emoji，或者徽章又退化成「一个圆 + 一条线」）：

- `tests/icons.test.mjs`：扫 `js/*.js` 与 `index.html`，出现 emoji 就红；
- 每个图标名都要真的存在（写错名字不会静默变方块）；
- 每个徽章必须有自己的字形、必须有花边渐变（改回扁平圆会红）；
- 徽章名必须带存档参数 `badgeLabel(state, x)` —— 少传一个参数，徽章墙 16 个名字会**全部变成空字符串**（v26 真踩过）；
- 线性图标必须在根 `<svg>` 上带描边 —— 这条是真踩过的坑：漏了之后所有图标「透明」，
  页面上只剩布局空位，肉眼要滑到设置页才发现；
- 真浏览器自检（`browser-check`）会数页面上的图标、兜底方块、缺尺寸、残留 emoji，
  并断言「徽章 ≥48px、设置图标 23px / 图标块 ≥34px、徽章名一个都不空」；
- 反向验证（`node tools/mutate-check.mjs`）故意把代码改坏，确认测试真的会红。
  **v27 修掉了这个工具从 v26 起的一个假绿灯**（临时沙箱漏了 `index.html` 等文件 → 基线本来就红 → 每条变异都算「抓到」），
  并如实区分「测试守得住」和「改坏后行为不变的等价变异」：现在严格捕获 117/117，另有 2 条半敏感、4 条等价变异单独标注。

**可复现**：`npm test`、`node tools/browser-check.mjs`（截图在 `.selfcheck/shot-phone-*`）、
`node tools/mutate-check.mjs`。

## 〇·六、更新提示（2026-10-22，v28~v29）

应用装到手机上之后，更新是「安静」发生的 —— 如果不说一声，使用者永远不知道改了什么。
所以做了两个弹窗，分工不同：

| 弹窗 | 什么时候出现 | 用户看到什么 |
| --- | --- | --- |
| **更新了什么** | 新版本**已经跑起来**之后，第一次打开 | 上次之后每一版的更新条目（1~4 条人话），点「知道了」关掉，同一版只弹一次 |
| **有新版本了** | 手机上跑的这版旧了、服务端已经有新版（启动后 4 秒、切回前台时检查） | 「新版本 vXX 已经准备好，刷新一下就能用上，记录不会丢」+「刷新」/「先不刷新」两个按钮 |
| **检查更新**（v29） | 用户主动点 设置 → 关于 →「检查更新」 | 没新版就说「已经是最新版本（vXX）」；有新版本就弹上面的刷新提醒 |

设计约束（别改）：

- **不自动强制刷新**：可能正在记一笔，打断输入比晚一分钟更新更糟；
- **不每次打开都弹更新说明**：只弹给「版本变过」的设备；
- 新用户（走完引导 / 看示例 / 第一次填资料）不会收到「更新说明」，那不是更新，是第一次装上；
- 离线 / 读不到服务端版本时静默跳过，绝不弹错误。

**发版三件事（缺一不可）**：

1. `js/version.js`：改 `APP_VERSION`，并在 `CHANGELOG` **最前面**加一条（version 必须等于新版本号、date 写 YYYY-MM-DD、items 1~4 条人话）；
2. `sw.js`：`CACHE` 与 `APP_VERSION` 一起升；新增的 js 文件加进 `ASSETS`；
3. 推送 → CI → `node tools/check-live.mjs && node tools/live-audit.mjs`。

**护栏**：`tests/version.test.mjs` 检查两边版本号一致、`CHANGELOG` 最新一条等于当前版本、版本从新到旧排列、
更新挑选逻辑（没记录过 / 跨版本 / 已最新）、以及「服务端比本地新」的判断方向；
`browser-check` 会造一个「上次看到的是上一版」的存档，断言弹窗真的弹出来、条目渲染出来，并截图
（`.selfcheck/shot-phone-8-update.png`）。
「刷新提醒」也进了自动化：`browser-check` 用 CDP 拦截页面里的 `sw.js` 请求、返回一个「服务端版本更高」的副本，
断言弹窗标题 / 两个按钮 / 假版本号，并截图 `shot-*-9-refresh.png`；「检查更新」按钮也断言「已经是最新版本」的反馈。

**可复现**：`npm test`（`tests/version.test.mjs`）、`node tools/browser-check.mjs`。

## 〇·七、说一句记不上怎么办（2026-10-25，v31）

反馈大意：「很多时候告诉 AI 吃了什么，AI 会说没看懂，很难记上，很影响记录积极性。」
查下来是几种情况混在一起，这次每种都做了兜底（下面这些都有自动化检查覆盖；真机手点还没做，见下文「为什么先停在试用」）：

| 以前 | 现在 |
| --- | --- |
| AI 听懂了，但食物库**没有这道菜** → 一条都不记，只回「库里没有」 | 按**同类食物的平均值**先记上（数字是本地写死的表，不是 AI 编的），界面标「估算」，克数能改、点 × 能删 |
| AI 返回的格式不标准：份量写成「一碗」、字段名对不上（有的用 items、有的叫别的）、服务商不支持「按固定格式回话」这种模式 → 被当成脏数据丢掉 | 都认：字符串克数 / 斤两 / 「一碗」/ 常见字段别名；不支持固定格式就自动去掉这个设置重试；返回空结果会再要一次 |
| 食物库太小、别名不全：酸奶 / 牛奶 / 蛋糕 / 小肉丸 / 馄饨 / 黄焖鸡米饭 / 酸菜鱼 这些要么认不出、要么只有离线/搜索一边认得 | 食物库 131 → 163 条；组合菜（一整顿）统一进同一份菜名目录，搜索、离线、AI 三条路共用；离线词典补全了别名 |
| 整句都没认出来 → 只能重说或手动记，容易放弃 | 给几个**能点的例句**、直接进食物搜索、原句不会丢（点「回到输入框改一改」会填回去） |

**注意**：按同类食物平均值先记上只在 AI 解析时生效；没配 AI 时不会解析「说一句」，
界面会直说「还没配置 AI」并给配置入口。

**兜底用的同类平均值表**写在 `js/foods.js` 的 `GENERIC_ESTIMATES` 里
（肉菜 / 主食 / 汤羹 / 甜点 / 饮料 / 零食 / 水果 / 蔬菜 / 家常菜），可核对、可离线复算；
界面上每一条估算都会写明「食物库里没有、按哪一类（肉菜 / 主食 / 甜点…）的平均值算的」。

> **v34 起这条策略升级了**（见下面〇·十）：本地库里没有的菜，先让 AI 直接估营养（本地校验后记上），
> 估不出来/过不了校验才用这张同类均值表兜底。旧规则「AI 一律不许输出营养数字」已经取消。

**可复现**：`npm test`（`tests/ai.test.mjs` / `tests/mealparse.test.mjs` / `tests/aicore.test.mjs` / `tests/foods.test.mjs`）；

## 〇·八、断签保护 + 打开时接住（2026-10-25，v32）

用户说：「需要一些能让用户更主动使用的东西，核心目的是每天有主动去用的想法。」
查下来，这类记录工具最常见的死法不是「功能不够」，而是**断签一次就再也不打开**：
连续记录归零、页面没有任何招呼、回来还要面对「你已断签 N 天」的指责。所以先做了最小的三件事：

| 场景 | 现在会怎样 |
| --- | --- |
| 今天一笔都没记 | 今天页最上面一张小卡片：「今天还空着 —— 先记一口也算，一句话就行」，点一下直接进「说一句」 |
| 今天记了、昨天空着（而且是老用户） | 问一句「昨天没记，要补一笔吗？」→「补记昨天」直接切到昨天记；「不补了」当天不再问 |
| 连续记录 | 第 1 天开始就显示；断了不会清零惩罚、植物也不会枯萎，今天记了就算重新开始 |

设计约束（别改坏）：

- **卡片放在今天页最上面**（不是 hero 下面）：360×640 小屏首屏也能直接看到按钮，不会被底栏盖住；
- **不指责、不显示「断签 N 天」**，只给最小动作；「昨天没记」一天只问一次；
- **新用户不催**：一条记录都没有时不显示任何卡片（交给欢迎页/引导）；
- **补记不是伪造**：只是把日期切到昨天、让用户自己记，系统不替用户填数；
- 没有惩罚性设计：不清零、不扣徽章、不显示「失败」。

**没有做的部分（受架构限制，别写成能做）**：真正的定时推送提醒。应用是纯静态网页 + 数据只在本机，
浏览器通知需要服务端推送；要做就得上后端，和「无后端、数据只在本机」冲突，需要单独决策（见 issue #14）。

**验收**：`tests/achievements.test.mjs` 断言「什么时候该出现、什么时候不该出现」；
`browser-check` 用两种真实存档跑界面：今天空着 → 点按钮进记录页且输入框聚焦；昨天空着 → 点「今天不补」后当天消失。
截图 `.selfcheck/shot-phone-12-nudge-today.png` / `shot-phone-13-nudge-yesterday.png`。

## 〇·九、覆盖类操作先留快照 + 两个窗口不互相盖（2026-10-25，v33）

独立审计（`.audit/arch-audit-v33.md`）发现三条会**静默覆盖真实记录**的路径。这类问题不会报错，
但代价是几个月的记录没了 —— 所以它排在所有新功能前面，而且每一条都补了测试。

| 场景 | 以前 | 现在 |
| --- | --- | --- |
| 打开演示链接 `?demo=1`（或欢迎页「看一个填好的例子」） | 直接清空整包存档、换成示例数据 | 有记录时先确认「会覆盖 X 天记录」，并**自动留快照**；看完可以回滚 |
| 从文件导入存档 | 只问一句「会覆盖，确定吗」 | 先自动留快照再覆盖；提示里说明去哪儿回滚 |
| 同时开两个窗口/标签页 | 后保存的把先保存的整包盖掉，无提示、找不回 | 另一个窗口写入时本页会提示并同步；正在填东西时不打断，关面板后自动补同步；本页拿旧数据去保存会**让路**，并说清「这一笔没记上」 |

设计约束（别改坏）：

- **快照只有一份**：升级 / 导入 / 看演示前都会覆盖它，但存的永远是「刚刚那份真实记录」，比更早的旧快照更有用；
- **不让用户选「要不要留底」**：留底不是可选项，直接做掉；
- **多窗口默认同步、不打断输入**：只在「面板开着 / 输入框有字」时挂一条提示，绝不把输入到一半的内容冲掉；
- 判断「有没有会丢的东西」只有一处（`js/store.js#hasUserData`）：记录、体重、自己加的食物、填好的资料都算。

**仍有限制（如实说）**：两个窗口同时开着、且都在同一天记不同的东西时，后保存的那一笔如果触发「让路」，
会提示没记上、需要再点一次；没有做真正的合并。这是「数据不会悄悄丢」和「两笔都不丢」之间的取舍 ——
宁可提示重做，也不静默覆盖。

**验收**：`tests/calc.test.mjs` / `tests/store.test.mjs` 覆盖范围与「有没有会丢的东西」；
`direct-check` 用真实界面走三条路径（演示确认/取消/确认后快照、多窗口同步、旧数据保存让路）；
反向验证：把修复临时关掉，`direct-check` 和单测都会红。

## 〇·十、AI 归位：直接估营养，存成「我的食物」（2026-10-25，v34，issue #12）

用户原话：「我接入 AI 是为了当个类似小助手，结果你让 AI 进库里找」。
问题不在代码，在规格：旧规则「AI 只给名字、热量必须由本地库算」把最会「看懂人话」的模型降级成了查表员。
v34 把这条规格推翻，改成「**AI 估、本地核**」。

| 场景 | 以前 | 现在 |
| --- | --- | --- |
| 说一道本地库里没有的菜（家里做的、新品牌） | AI 给个名字，库里没有 → 只能按同类均值估，或干脆记不上 | AI 直接估**这一份**的热量/蛋白/脂肪/碳水 → 本地校验 → 记上并标「AI 估的」 |
| 同一道菜第二次说 | 再问一次 AI（每次数字可能都不一样） | 第一次保存时就存进「我的食物」；再说只要句子不复杂，**本地直接算，零 AI 请求** |
| AI 给的数字离谱/自相矛盾 | —（以前根本不让它给） | 本地挡住：每 100 克 >900 kcal、营养素 >100 克、4/9/4 差 >50% → 退回同类均值并说明原因 |
| 换了不支持新格式的模型/服务商 | — | 老格式（只有名字+克数）继续能记上，不会退化成「一条都记不上」 |

**数字是怎么被核对的**（这是「敢让 AI 估」的前提）：

1. 份量与上下限：每 100 克热量 ≤ 900、任一营养素 ≤ 100 克（和读营养成分表共用同一组上限）；
2. 4/9/4 对账：蛋白×4 + 脂肪×9 + 碳水×4 与 AI 给的热量差 **30%~50%** → 按营养素重算热量并标注；
   差 **>50%** → 认定自相矛盾，整条退回本地同类均值；
3. 界面上标「AI 估的」，保存后告诉你「存了几样进我的食物」，来源和原句一起存在本机（可导出、可核查）。

**省请求的边界（保守）**：只有「名字 + 份量/餐次/口语词」这种句子才走本地（例如「下午又吃了某网红限定轻食碗 200 克」）；
只要还有别的吃的或没认出来的词（「……和一个苹果」），就照常调 AI —— 宁可多花一次请求，也绝不悄悄漏记。

**测试**：`tests/ai.test.mjs`（优先级 / 估算 / 校验退回 / 我的食物 / 省请求）、`tests/aicore.test.mjs`（营养字段收敛）、
`tests/label.test.mjs`（4/9/4 校验）、`tests/store.test.mjs`（我的食物来源与同名去重）；
`direct-check` 三·三节在真实浏览器里走完「AI 估 → 核对 → 保存 → 再说一次命中 + 0 次请求」。
那条「永远会通过」的假测试也换成了真断言（issue #18）。

**没验的**：本机没有可用密钥，AI 估出来准不准全部用「按真实返回形状写的假上游」验；真模型的手感等 #6 反馈。

## 〇·十三、慢网首屏不再误报「没能打开」（2026-10-25，v37）

发布验证时踩到的真问题：线上冷启动要按顺序下载 30 多个模块，慢网/代理下实测 **14 秒**；
而首屏兜底脚本以前 4 秒就弹「没能打开」——用户会先看到一张错误卡，过几秒又自己好了，像是工具坏了。

现在：

| 情况 | 以前 | 现在 |
| --- | --- | --- |
| 第一次打开、网络慢，模块还在下载 | 4 秒后弹「没能打开」（假的） | 先显示「正在打开…（第一次打开、网络慢会多等一会儿）」 |
| 应用真的启动 | 错误卡可能还挂着 / 白色页面 | 「正在打开」和「没能打开」都自动收起 |
| 模块真的加载失败（语法错、404） | 4 秒后提示（这个要快） | **错误监听立刻**显示「没能打开」，不用等超时 |

顺带修了 `live-audit` 的假红：它以前「兜底卡一出现就继续跑」，慢网下会误判「欢迎页没有入口」并 null.click 崩掉；
现在先老实等应用启动（最多 40 秒），超时且没兜底卡才报「首屏没启动」。

**没验的**：真机慢网（3G/弱信号）的等待体感；首屏加载态没有自动化测试（记账为 G5）。

## 〇·十四、30 天回顾 + 更新不再卡住（2026-10-26，v38，issue #14 C）

### 一、「最近 30 天回顾」

「我的成长」里新增入口：看最近 30 天记了几天、最长连续、蛋白达标天数、运动分钟、体重趋势、最常记的几样。
只陈述事实、不评价；体重只报趋势并注明「单次波动不用当真」；记录不满 3 天直说「先记几天」，不编数字。
实现是纯函数 `js/recap.js`，8 条单测钉住窗口边界/数据不足/只读/文案不评判。

### 二、更新机制加固（真事故）

用户手机截图里出现了**早已修掉的旧行为**（「认出来了，但本地库里没有 → 一条都没记上」）。
查下来：那是 v30 以前的版本。早期 Service Worker 是**缓存优先、连 `sw.js` 都缓存**，
于是手机上永远读到旧版本号、更新提醒永远弹不出来 —— 装上一次就再也升不了级。
v28 起已修（`sw.js` 不走缓存），但已经卡住的手机会一直卡着。现在补三条：

| 机制 | 说明 |
| --- | --- |
| 启动自动更新 | 打开应用、发现线上版本更新、而且用户还没动手（没开弹层/没草稿/没在输入）→ 自动清缓存重载一次，记录不丢 |
| 常驻横幅 | 不方便自动更新时，顶部挂一条「有新版本 vXX，点这里更新（记录不会丢）」，**不会被「先不刷新」关掉** |
| 自救页面 | 已经卡死的旧版：打开 [`update.html`](update.html) → 注销旧 Service Worker、清临时缓存、重载。**不碰 localStorage**，记录/资料/密钥都在 |

「我的 → 关于」也加了 **强制更新** 按钮和版本号显示；以后截图那一行就能知道手机上跑的是哪一版。

**回归测试**：`direct-check` 三·四节用用户截图里的原句「早饭 喜茶苦巧咸酪碎银子少少甜」走真实界面，
断言必须记上、标「AI 估的」、存进「我的食物」，并**明确断言不许再出现「一条都没记上」的旧文案**。

**没验的**：真机上的更新体验（等 #6）；卡在很老版本的手机需要手动打开一次 `update.html`（这是唯一入口）。

## 〇·二十二、更新逻辑改对了：打开就是新版，开着才提示（2026-10-27，v46）

用户纠正了 v45 的方向：

> 逻辑应该是每次打开网页时都应该是最新版本，然后网页一直开着，有更新了主动在已打开的网页提示。

也就是说 v45 做的「打开旧版 → 顶部提示你去更新」是错的：**不该先把旧版塞给用户再让他点**。

### 两条规则（分别对应两处代码）

| 规则 | 谁负责 | 做法 |
|---|---|---|
| **A. 每次打开都是最新版** | `sw.js` | 缓存策略从「先用缓存 + 后台更新」改成**网络优先**：先要最新的，拿到就用并存下来；拿不到（断网/超 2 秒）才用缓存 |
| **B. 页面一直开着时，发新版要主动提示** | `index.html` 内联脚本 | 启动查一次 + 每 60 秒（仅页面可见时）+ 切回前台 + 网络恢复，四个时机各查一次 |

### 为什么之前必然是旧版

原来是 stale-while-revalidate：命中缓存立刻返回，网络请求在后台跑。优点是打开快，
**代价是「打开的这一刻永远是上一次的版本」**，新版要「再打开一次」才进来。
用户看到的「新开网页还是旧版、得手动刷新」就是这么来的 —— 这不是提示没做好，是策略选错了。

改成网络优先后：

- 正常网络：先拿到最新的 HTML/JS，直接就是新版（`cache: 'no-cache'` 保证不会被浏览器自己的
  10 分钟 HTTP 缓存糊弄过去，有 ETag 时是 304，很快）；
- 断网：`navigator.onLine === false` → 直接给缓存，不等；
- 弱网：最多等 2 秒，超时先给缓存，网络请求继续在后台跑完（下次打开就是新的）。

### 「一直开着」这一半

以前内联脚本只跑一次（页面解析时），页面开着不动就再也不查了。现在：

- 每 60 秒查一次（**只在页面可见时**，后台标签页不查，省电省流量）；
- 切回前台立刻查（用户回来了，正好把新版递到眼前）；
- 网络恢复立刻查（刚才断网查不到，接上就可能已经有新版）；
- 一旦提示过就停（`shown`），不会一分钟一个请求。

提示出现后**不会偷偷重载** —— 页面保持原样，什么时候更新由用户点。

### 自检（`tools/update-check.mjs` 按新语义重写）

在临时副本里模拟发版，分三段验：

1. 第一次打开 → 版本正确、缓存建立、没有横幅；
2. 改成 v99 后**新开一个网页** → 断言**直接就是 v99**（不是「v46 + 横幅」），且 Service Worker 也换到 `fatloss-v99`；
3. 页面保持打开再改成 v100 → 派发 `visibilitychange` → 断言横幅出现、页面仍是 v99（没被偷偷重载）→ 点横幅变成 v100、localStorage 里的标记还在。

**总账**：R60 改写为「打开就是最新版（网络优先）」，新增 R61「一直开着要主动提示」、
R62「更新只清代码缓存、不碰 localStorage」；62 条规则 / 61 条有测试。

Pages 发布成功（[run 40522445292](https://github.com/kotochain/fatloss-helper/actions/runs/40522445292)）；

## 〇·二十一、修好「打开是旧版、还没有更新提示」（2026-10-27，v45）

用户真机反馈：**新开网页看到的是上次那个旧版本，顶部没有任何提示；手动刷新一下就变新版了。**

查下来是两个问题叠在一起：

1. **打开时页面本来就是旧版** —— Service Worker 的策略是「先用缓存、后台更新」，这是 PWA 的常态，
   不是 bug；但配套的「有新版本」提示必须补上。
2. **提示不出现** —— 版本检查放在 `app.js` 里，用 `fetch('sw.js', { cache: 'no-store' })` 去读线上版本号。
   线上 `sw.js` 带 `cache-control: max-age=600`，前面还有 Fastly CDN（`x-cache: HIT`）。
   `no-store` 只绕浏览器缓存、**绕不过 CDN**，读回来的是旧版本号 → 一比「已是最新」→ 什么都提示不了。
   再加上检查要等 4 秒，用户早就自己刷新了。

**修法**：

- `index.html` 里加一段**内联**的版本自查：页面一解析就 `fetch('sw.js?ts=' + Date.now())`（带时间戳 = 每次都回源），
  和 HTML 里写死的 `HERE` 比；不一样就把顶部横幅亮出来「有新版本 vX，点这里更新（记录不会丢）」。
  点横幅 = 注销旧 Service Worker + 清代码缓存 + 重载，**不碰 localStorage**（记录、资料、密钥都在）。
- `app.js` 的 `deployedVersion()` 也加上 `?ts=`（同一个 CDN 坑）；启动检查从 4 秒提前到 1.2 秒。
- `app.js` 的常驻横幅改为**避让**内联横幅（同一条信息不叠两层），它只在「内联那步没成功」时兜底。
- 版本号写死在 HTML 里是刻意的：它必须等于 `js/version.js` 的 `APP_VERSION`，由 `tests/version.test.mjs` 守着。

**验证**：新增自检 `tools/update-check.mjs` —— 把项目复制到临时目录，让浏览器缓存当前版本，
再把副本版本号改成 v99 模拟发版，新开页面断言「横幅立刻出现 + 点完真的换成新版」。
实测：旧版打开 **刚起来就有横幅**，点击后变成 v99，横幅消失。

**顺带踩到的坑（写下来免得再犯）**：macOS 上 `/var` 是 `/private/var` 的符号链接。
给 `serve.mjs` 传绝对路径时，它内部的 `isMain` 判断（`path.resolve(argv[1]) === fileURLToPath`）会失败，
进程**以退出码 0 悄悄退出、什么都不打印**，看起来像「服务起不来」。临时目录必须先 `realpathSync`。

**发布记录**：提交 `5c8870e`；CI 4 个 job 全绿（[run 40513892312](https://github.com/kotochain/fatloss-helper/actions/runs/40513892312)），
Pages 发布成功（[run 40513892309](https://github.com/kotochain/fatloss-helper/actions/runs/40513892309)）；
`check-live` 线上 v45、34 个文件逐字节一致、缓存名 `fatloss-v45`；`live-audit` 0 个阻断问题。

## 〇·十五、AI 不再说「我没认出来」（2026-10-27，v39，issue #20）

做 #20 时先给的方案是「离线漏识别 → 给补记入口，让用户自己填热量」，用户当场否了：
**「AI 就是用来估热量的，为什么会有手动环节？」**

真正的问题不在「补记」，在文案和兜底逻辑：AI 请求失败/普通模式时，代码静默退回本地词表，
再弹一句「这句话里的『佛跳墙』我没认出来」—— 用户看到的是「AI 是个弱智」，而不是「AI 没连上」。

现在钉死三条（已进《产品逻辑总账》R55/R56）：

1. **AI 永远不说「不知道 / 没认出来」**：不确定就追问，但必须先给一版估算；
2. **用户可以回答「我也不知道」**：AI 必须自己按常见份量估，不能把问题再推回给用户；
3. **只有普通模式/请求失败才用本地清单**：文案要说清是「本地清单里没有」，并给「用 AI 重新解析」的出口。

| 以前 | 现在 |
| --- | --- |
| 本地清单没认出的东西，只弹一句「我没认出来」，点不了 | 说明「本地清单里没有「X」」+ 原因（普通模式 / AI 没连上），旁边就是「用 AI 重新解析这一句」 |
| AI 的追问只能看，没法回答 | 可以补一句重新估；也可以点「我也不知道，你按常见的估」，点了就不再追问 |
| 普通模式下点重试可能偷偷发请求 | 先问一句「会发一次请求（可能产生费用）」，同意才走 |
| 「模型只给名字」只有单测 | 假上游只回名字 → 真界面必须出现带「估算」的可保存条目 |

**验证**：387 单测全过、反向验证严格 119/119（新增 2 条提示词变异）、`direct-check` 三·二/三·五 新增断言、
`browser-check` 新增「佛跳墙和米饭」场景。

**没验的**：真模型是否照提示词追问（取决于服务商和模型），留在 #6。

## 一、怎么用起来（安卓手机）

### 第 1 步：在电脑上启动一次预览服务

```bash
node tools/serve.mjs
```

终端会打印两个地址，例如：

```
本机打开：  http://127.0.0.1:4173/
手机打开：  http://192.168.1.23:4173/   （手机需连同一个 Wi-Fi）
```

### 第 2 步：手机浏览器打开「手机打开」那个地址

用安卓自带的 Chrome 或 Edge 打开。第一次打开是「填写资料」页。

### 第 3 步：添加到主屏幕

Chrome 右上角「⋮」→「添加到主屏幕」/「安装应用」。之后桌面会出现图标，点开是全屏的，**和 App 基本一样**，而且断网也能用。

> 为什么不做成真正的安卓 App：那需要装安卓开发工具、签一个安装包、每次改动重新打包安装。这个网页版能立刻用、能随时改，以后真想上架应用商店，现在这套界面和算法可以原样搬进安装包里，不用重做。

### 第 3.5 步：接上 AI（可选，强烈建议）

不接也能用（走离线识别，常见说法能认）。接上之后，你怎么写都能听懂。

**在手机上配（推荐）：** 「今天」页或「记录」页右上角 → **AI 设置** →

1. **选服务商**：DeepSeek ★ / 通义千问 / Kimi / 智谱 GLM / 硅基流动 / OpenAI / 本地模型(Ollama) / 自定义
2. 接口地址会**自动填好**（也可以自己改，支持自定义端口、公司内网地址）
3. 点 **「获取模型列表」** —— 直接问服务商有哪些模型可选，**自动选中一个合适的**
   （会优先选新版轻量对话模型，跳过 legacy / 预览版 / 推理模型 / 向量模型）
4. 去服务商后台创建 API Key（说明里有「去拿密钥 →」直达链接），粘贴进密钥框
5. 点「保存并测试连通」——成功会显示模型的实际回复；失败给中文原因（密钥错 / 余额不足 / 模型名不存在 / 连不上）

**密钥存在哪？** 存在你这台手机的浏览器里，只发给上面那个服务商。
「手机丢了会泄露密钥」的风险由你决定是否接受——在意的话：
- 随时可以在设置里点「清除密钥」；
- 或者把连接方式切成 **「走电脑中转」**（密钥存你自己电脑上，但要开着电脑、手机同一个 Wi-Fi）。

**浏览器能不能直连，我实测过**（2026-10-16，用 OPTIONS 预检）：

| 服务商 | 浏览器直连 |
| --- | --- |
| DeepSeek / 通义 / Kimi / 硅基流动 / OpenAI | ✅ 可以 |
| 智谱 GLM | ❌ 不行（界面上会自动建议你选「走电脑中转」） |
| 本地 Ollama | ✅ 可以（但要在电脑上装好模型） |

### 第 4 步：发布成真正的网址（推荐，一次设置永久有效）

配好第 3.5 步的手机直连之后，**这台电脑就再也不需要参与了**。把应用发布到 GitHub Pages，
你手机上打开那个网址、加到主屏幕，就是一个真正的 App：随时能开、断网也能用、AI 也能用。

**你需要做的（约 5 分钟，只需一次）：**

1. 建仓库并推送代码（在本项目目录执行，把 `你的用户名` 换成你的 GitHub 用户名）：

```bash
git remote add origin https://github.com/你的用户名/fatloss-helper.git
git branch -M main
git push -u origin main
```

2. 仓库页面 → **Settings** → **Pages** → Source 选 **GitHub Actions**（保存）
3. 等 1 分钟，Actions 里会跑「发布到 GitHub Pages」；完成后网址是：
   `https://你的用户名.github.io/fatloss-helper/`

**注意**：GitHub Pages 默认是**公开**的，也就是别人能访问这个网址（但看不到任何人的记录——
记录只存在各自手机的浏览器里，不会上传）。如果你希望网址不公开，可选：
- 仓库设为 Private（GitHub Pages 的私有仓库发布需要付费账号）；

**第一次发布后**：你自己打开这个网址 → 浏览器菜单「添加到主屏幕」→ 在「AI 设置」里填一次密钥。之后就不用管了。

## 二、它到底算得准不准

诚实说明，分三层：

### 0. 食物库：默认按「熟重」算（v30）

肉和鱼拆成了「熟重」「生重」两条：

- 说「鸡胸肉」「牛肉」「虾」→ 按**做熟后的重量**算（普通人称/估份量都是这个）；
- 说「生鸡胸肉」「生重」→ 才按生重算；
- 主食本来就分生熟（米饭、面条按熟重）；餐单和教练建议也统一按熟重给克数。
- 熟重不是统一乘一个系数：肉类约 ×0.75（烹饪失水约 25%），三文鱼熟重≈生重、虾约 +6%，各自按实际折算。

为什么这么做：100 克生鸡胸 118 kcal，做熟后 100 克约 157 kcal。按生重算熟食会少算两成多，
这是最容易让人以为「我明明吃得不多却掉不了秤」的一类误差。**以前的记录不会被改**（记录里存的是当时的食物数据）。

### 1. 算「你每天该吃多少」用的公式

- 基础代谢：Mifflin-St Jeor 公式（有体脂率时改用 Katch-McArdle），这是国际减重指南里最常用的公式，**误差一般 ±10%**。
- 每日消耗 = 基础代谢 × 活动量系数（久坐 1.2 ～ 非常高 1.9）。
- 热量缺口：按「每周减掉体重的 0.25% / 0.5% / 0.75%」换算，1 公斤脂肪按 7700 kcal 估算。
- 分配顺序是 **蛋白质 → 脂肪 → 碳水**：蛋白质 1.8 g/kg（80 kg 以上降到 1.6，且不超过总热量 35%）；脂肪 0.8~0.9 g/kg（不低于 0.6 g/kg 的安全线）；剩下的热量才是碳水，且碳水不低于 80 g。
  这个顺序很重要：反过来先定碳水，会算出「根本放不下」的脂肪目标（例如 100 kg 的人要 90 克脂肪），用户照着吃只会让脂肪永远差一半。

因为公式本身有 ±10% 的误差，**真正的校准靠体重趋势**：「体重」页会根据实际掉秤速度告诉你该多吃还是少吃（这个方法比任何公式都准）。

### 2. 内置的 163 种食物数据

- 主要参考《中国食物成分表》的常见条目和市售包装食品标签的典型值，对主食区分生熟。
- 每一条都做了自检：`蛋白质×4 + 脂肪×9 + 碳水×4` 必须和标称热量对得上（含酒精的除外），对不上就会被测试拦住。这一关已经抓出并修正了 30 条之前抄串的数据（例如「虾 93 kcal」却配了 2.8 g 碳水）。
- **炒菜、外卖、家常菜的误差最大**（同一道菜不同人放油差一倍），这几条只当参考。
- 少部分条目用的是更贴近日常吃到的口径，不完全是成分表的数：全脂牛奶按市售包装标签、鸡胸肉/红薯/西兰花/三文鱼按 USDA。两张表的口径差可达 ±20%，所以别当精确值用。
- **烹调油单独算**：餐单里会明确写出「全天烹调油 X 克，已算进总数」，避免出现「菜单不含油、提醒又让你加油」导致每天多吃一两百 kcal。
- **包装食品请照包装背面的营养成分表自己建**（「记录」页 → 新增自定义食物），那才是精确的。拍照读表读出来对不上时，它会直接劝你重拍，不让你对着错数字发愁。

### 3. 安全边界（代码里写死的，不是提示文字）

- 每天热量不低于基础代谢的 1.1 倍，且女生不低于 1200 kcal、男生不低于 1500 kcal；
- 每周减重不超过体重的 1%；
- 脂肪不低于 0.6 g/kg，碳水不低于 80 g；
- BMI 低于 18.5（偏瘦）时不给减脂缺口，直接劝退；目标体重低于 BMI 18.5 也会警告；
- 年龄填不满 18 岁会拒绝计算；
- 资料填错填漏时保存会被挡住（不会出现「身高清空 → 目标热量静默掉到 1200」这种事）。

### ⚠️ 不适用的情况

这个工具只做估算和记录，**不是医疗建议**。以下情况请先问医生，不要照这里的数字吃：

- 怀孕或哺乳期
- 有甲状腺、肾脏、糖尿病、进食障碍等疾病
- 正在服用影响体重的药物
- 未满 18 岁

## 三、功能

| 页面 | 做什么 |
| --- | --- |
| **今天** | 还能吃多少 kcal、三大营养素差多少、按餐列出吃了什么、今天的运动；「问教练」给具体到食物的下一步（不配 AI 也给本地版，配了 AI 才会多花一次请求说细一点） |
| **记录** | 搜索 163 种食物 + 组合菜（支持俗称，如「地瓜」「美式」「奶茶」），支持「150克 / 2个 / 一小碗 / 半斤」这类写法；点某一餐能直接说一句；只知道热量时可以「只填热量」（不用先找食物）；也有自定义食物 |
| **推荐** | 按你的热量和蛋白质目标算出每餐吃什么、吃多少克（含烹调油额度）；「今天练什么」按你当天能用的器械出有氧方案，并支持换器械的替代动作；另有走路目标 |
| **体重** | 记体重、看趋势图、按实际掉秤速度给出「该多吃还是少吃」的建议；导出/导入存档 |

几个设计上的取舍：

- **运动消耗一点都不加回额度**（连一半都不加）：活动量已经在目标里算过一次，再加回来就是双算。练的那天缺口自然更大，这是有意设计的。
- **份量都是整份/半份**：不会建议「吃 0.37 个鸡蛋」；配餐时主菜有热量上限，保证主食和蔬菜有位置。
- **餐单是起点不是规定**：换一套按钮可以换菜；「记入今天」之后按实际吃的改。
- **餐单会同时盯住热量、蛋白、脂肪、碳水四项**：只盯热量和蛋白的话，实测会出现「脂肪只有目标的一半」而用户不知道。

### 上线前必须跑什么（2026-10-20 定，血泪版）

之前的自检是绿的，但用户手机上仍然踩到白屏、按钮点不动、AI 模式从来没工作过。
复盘下来不是「测得少」，是**测的方向不对**：只测「我做过的功能」，不测「用户能点到的东西」；
只跑本地文件，不跑线上部署；只断言「没报错」，不断言「数字对不对」。现在按下面这条链走：

| 阶段 | 跑什么 | 它到底在守什么 |
| --- | --- | --- |
| 改代码时 | `npm test` **连跑 2~3 次** | 逻辑正确；重复跑排除偶发通过 |
| 改代码时 | `node tools/mutate-check.mjs` | **测试本身有效**：故意改坏代码，测试必须变红 |
| 提推送前 | `quicklog-check` + `offline-check` + `sweep-check` + `resilience-check` + `layout-check` | 真浏览器里点得动、断了网能用、存档坏了不丢数据、小屏和大字号不烂 |
| 推送后 | `node tools/check-live.mjs` | 线上文件和本地**逐字节一致**、版本号真的更新了 |
| 推送后 | `node tools/live-audit.mjs` | **真的打开线上网址**走一遍：引导、记一笔、重开、断网、老存档、导出/导入、图标与主题色、启动失败兜底 |

两条纪律（都是从事故里来的）：

1. **本地文件一致 ≠ 线上能用。** `check-live` 只证明文件传对了；只有 `live-audit` 证明「跑起来是对的」。
2. **新写的检查必须反向验证。** 故意弄坏一个东西，确认检查会报红；不报红就是摆设。
   这条抓出过：自检脚本自己写错字段名、监听的下载目录根本没生效、断言只匹配到「前 12 条」。

### 协作与开发流程

- 提交 Issue：`.github/ISSUE_TEMPLATE/` 里有「报告问题」「想要新功能」两个模板，问得比较具体（哪一页、实际 vs 期望、截图）。
- 提 PR：见 [CONTRIBUTING.md](CONTRIBUTING.md)，里面有四条硬规矩（不许提交密钥、改了行为必须补测试并做反向验证、算法改动要给独立核算、不要把「读了代码」说成「验证过」）。
- CI：`.github/workflows/ci.yml` 在每次推送跑测试、反向验证、密钥自查、缓存清单检查，以及真浏览器自检。
- 发布：`.github/workflows/pages.yml` 把应用发布到 GitHub Pages（仓库 Settings → Pages → Source 选 "GitHub Actions"）。

### 目录结构（新增部分）

```
js/ai-core.js         AI 提示词、请求、结果收敛（浏览器直连与电脑中转共用一份）
js/ai-config.js       本机配置存取（纯逻辑，可测试）
js/ai.js              AI 门面：直连 / 中转 / 离线三条路径的自动选择与兜底
js/providers.js       服务商预设、模型列表排序、掩码
tools/direct-check.mjs 直连 + 日历的端到端自检
tools/chrome-path.mjs  跨平台找 Chrome（本机 macOS / CI 的 Ubuntu 都能跑）
.github/               CI、Pages 发布、Issue 模板
```

### 已知限制

- 食物数据是估算值，炒菜类误差最大；没有接入任何在线食物库（这是为了「不联网也能用」）。
- 脂肪目标在少数组合下只能达到 80% 左右：主食按「整份/半份」取整时会挤掉一点脂肪额度。要精确到克得自己称油。
- 餐单里的主食是「换算成米饭/燕麦的克数」，不是强制吃米饭——同类主食可以等量替换。
- 没有账号系统，所以只有一台设备能看到记录（多设备要手动导出/导入存档）。
- 修改 JS 后需要在手机上刷新两次才能拿到新版本（离线缓存机制）。发版时按 `README` 〇·六 的三件事做：
  `js/version.js`（版本号 + 更新说明）、`sw.js`（CACHE/APP_VERSION/ASSETS）、推送后跑线上检查。
- 没有做图片识别、条码扫描——这两件事需要联网服务和授权，暂时不做。
- AI 只在手机能和电脑连同一个 Wi-Fi 时可用（密钥不放手机上的代价）。出门在外自动退回离线识别。
- 配置只支持一个服务商（换家就是改一下设置）。如果以后想给多个人用，需要各自一份配置。
- 本地模型（Ollama）虽然免费且数据不出本机，但在普通笔记本上解析一句话可能要十几秒，体验不如云端。
- 离线识别是规则匹配，生僻说法认不出来（会明确说认不出来，不瞎猜）；接上 AI 后这个问题基本消失。
- 有氧动作的 METs 是通用值，个人的实际消耗会差 ±20%。
