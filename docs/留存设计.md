# 留存设计：让人「每天主动打开」（2026-10-25）

> 用户原话：「我们需要一些能让用户更主动使用的东西，可以是趣味性的或别的都可以，核心目的是让用户保持每天有主动去用的想法……或者像多邻国那种？」
>
> 这份文档是提案，不是已经做出来的功能。**先看第 0 节的结论，再挑一条往下做。**

## 0. 结论先说

现在已经有的正反馈：连续记录天数、16 枚徽章、小植物成长、每周洞察、更新弹窗。
它们的问题不是「不够多」，而是**都在应用里面**：用户不打开就看不到，所以不构成「主动打开的理由」。

缺的是两样东西：

1. **今天非来不可的理由**（不是「有空看看」，而是「今天还有件事没做」）；
2. **断签时的安全网**（断了就再也不想打开，是这类工具最常见的死法）。

按「性价比 × 风险」排序，建议这么做：

| 顺序 | 做什么 | 工作量 | 为什么先做它 |
| --- | --- | --- | --- |
| **B（先做）** | 断签保护 + 打开时接住 | 小（约半轮） | 直接降低「放弃率」，不增加任何压力；和现有连续记录/植物天然衔接 |
| **A（再做）** | 「今日两件事」小目标 | 中（约一轮） | 给每天一个具体、10 秒能完成的理由；和徽章/植物打通 |
| **C（可选）** | 每周/每月「成长回顾」 | 中（约半轮~一轮） | 提供回访理由和成就感，但偏被动，适合放后面 |
| ✗ | 系统级定时推送 | 做不了（见 §4） | 静态网页 + 无后端，没有真正的定时通知能力；不要承诺做不到的事 |

不建议做：排行榜 / 好友 PK / 打卡群 / 付费会员墙。这是**一个人自己用的工具**，
社交压力会让「记错一顿」变成「不想面对」，和减脂这件事的心理相反。

## 1. 先看清：为什么不主动打开

- 打开应用 = 承认「我今天吃了什么」。这件事本身有心理成本，尤其吃得不好的那天。
- 现有正反馈（徽章、植物）**只在打开后才出现**，无法把人叫回来。
- 连续记录一断，用户会觉得「已经废了」，干脆不记 —— 这是 Streak 类设计最大的副作用。
- 没有「今天还剩什么没做」的明确提示，只有「还能吃多少 kcal」——后者是压力，不是动力。

所以留存设计的目标不是「更好玩」，而是：**让打开的成本更低、收益更即时、断了也能接上。**

## 2. 三个方向（具体到能开工的程度）

### B. 断签保护 + 打开时接住（建议先做）

做三件小事：

1. **断签不归零，改成「可以补」**：
   昨天没记、但今天记了 → 连续天数从今天重新算，同时给一句「断了也没关系，今天接上就行」，
   而不是把数字清零、什么都不说。植物已经这么做了（按累计天数生长），连续记录也统一成这个口径。
2. **允许补记昨天**：今天记完，如果昨天是空的，问一句「昨天要不要补一笔？」点进去直接记到昨天
   （记录本来就能选日期，只差一个入口）。
3. **打开时的一句「接住」**（不是系统推送，只是打开应用时看到）：今天还没记 → 今天页顶部一句话，
   不指责、给最小动作：「今天还空着。先记一口也算 —— 说一句就行。」点了直接进「说一句」。

**为什么是这个**：不需要新概念、不加压力、改动小，命中「断了就再也不打开」这个真实死因。
**风险**：几乎没有；唯一要注意的是别说教、别用「你已断签 3 天」这种话。
**要拍板的点**：现在有 3 枚「连续记录 7/14/30 天」徽章（`js/achievements.js`）。
如果连续记录改成「断了可以补」，这 3 枚徽章的达成条件也要跟着定义清楚（补记算不算、按自然日还是按记录日），
否则会出现「界面说没断、徽章却判你断了」的矛盾。

### A. 「今日两件事」小目标（第二轮做）

每天给 2 个**当天能完成、10 秒能做完**的小目标，例如：

- 记满两餐（早餐+午餐，或午餐+晚餐）；
- 蛋白达到当天目标（现在已有蛋白进度条，只差「达标了」这个确认）；
- 今天走了目标步数 / 记了一次运动（有运动记录时）。

完成就勾上、给一句具体反馈（「今天蛋白够了，108 克」），两件都完成 → 小植物浇一次水 / 加一点成长值。
**不做**：惩罚性任务、倒计时、「未完成会掉段位」。目标是「今天有事可做」，不是「今天必须做满」。

**为什么是两件事**：多邻国的核心是「每天一个小目标 + 连续天数」，但它有语言学习的天然课程结构；
减脂没有「今天的第 3 课」这种边界，所以用「记录 + 蛋白」这两个现有数据能算出来的目标最稳。
**风险**：任务化可能让用户为了勾任务而乱记（比如随便记一口凑数）——所以目标要跟「记录质量」弱相关、
且不做「连续完成 30 天」这种硬指标。

### C. 每周 / 每月「成长回顾」（可选）

每周一（已有周报基础）或每月 1 号，生成一张本地回顾：掉了多少、记了几天、最常吃什么、
蛋白达标几天、运动几次。纯本地算、可截图分享（不联网、不带个人隐私）。
**为什么**：给「坚持了一个月」一个可见的交代，也是拉回流失用户的理由。
**风险**：偏被动，用户不打开还是看不到；所以只能当补充，不能当主力。

## 3. 多邻国那套，哪些能抄、哪些不能

| 多邻国机制 | 适不适合 | 说明 |
| --- | --- | --- |
| 连续天数（streak） | ✅ 已有 | 但必须配「断签保护」，否则是压力源 |
| 每日目标（daily goal） | ✅ 可抄 | 改成「今日两件事」，用现有数据算 |
| 连胜冻结 / 补签 | ✅ 强烈建议 | 就是上面的 B |
| 阶段性勋章 | ✅ 已有 | 16 枚徽章 + 小植物 |
| 排行榜 / 好友 | ❌ 不做 | 一个人的减脂工具，社交比较会制造焦虑 |
| 推送提醒 | ❌ 做不了 | 见 §4 |
| 付费会员 | ⏸ 暂缓 | issue #1，等「做大做强」再说 |

## 4. 为什么「定时提醒」现在做不了（要说实话）

应用是 GitHub Pages 上的纯静态网页，数据只存手机本地，**没有服务器**。
浏览器的通知需要「服务端推送」才能在你没打开网页时送达；而本项目刻意没有后端
（这也是「数据只在本机、断网能用」的代价）。

能做的替代：
- 打开应用时提示（不是推送，用户得先打开）；
- 安卓「添加到主屏幕」后，系统可能会限制后台，网页无法自己定时唤醒 —— 不要依赖；
- 如果以后真要做推送，需要加一个后端 + 用户订阅，这会改变「无后端、数据只在本机」的产品前提，
  要单独决策，不能顺手加。

## 5. 怎么验收（先定指标，再动手）

产品没有埋点（数据只在手机本地、无后端），验收不能靠「后台看留存曲线」，只能这样：

- **本地可算的**：连续记录天数、每周记录天数、平均每天记几餐、蛋白达标天数占比 —— 加一个只读的「统计」函数
  （类似现有 `js/insights.js`），在界面上能看到，测试里能用假数据断言。
- **只能靠人**：用户自己（或女朋友）用一周后，在 issue #6 里回答三个问题：
  ① 这周有几天是「主动想打开」的？② 哪次想打开但没打开、当时卡在哪？③ 断签时看到那句话是什么感觉？
- **成功标准（先粗定）**：做完 B 之后两周，每周记录天数从现在的实际情况 +1 天以上；
  做完 A 之后，每天打开两次以上（记早餐/记晚餐各一次）的天数占比 ≥50%。
  达不到就回滚或换机制，不要硬堆功能。

## 6. 如果要做，先做哪一个？

建议：**先做 B（半轮）**，然后看真机反馈（#6）再决定 A 的具体目标怎么定。
理由是 B 改动小、风险低、直接对症；A 需要先知道用户真实的记录习惯（一天记几餐、蛋白达不达标），
而这些数据要等 #6 用一周之后才有。
